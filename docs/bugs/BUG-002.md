# BUG-002: Address bar switches back to the story while the report form is on screen

| Field | Value |
|---|---|
| Severity / Priority | Low / P3: refresh, bookmark or share of the page leads to the story, not to the form the reader sees. Mainly affects keyboard and assistive-technology users |
| Environment | Production, desktop kumparan.com. Google Chrome, no ad blocking, no test fixtures. Re-verified 2026-10-11 |
| Account | Guest |
| Reproduction rate | **Keyboard path: about 9 in 10 openings on desktop (20/22 on 2026-10-11).** Mouse-wheel scrolling 0/6, End key 0/6 (desktop + mobile). A click that jumps the page to the link: desktop 3/3, mobile 1/3 |
| Automated check | TC-RPT-012 (`tests/web/report/TC-RPT-012_Keyboard_Report_Keeps_Form_Url.spec.ts`): repeats the keyboard path 3 times and requires the URL to stay every time; known defect (`test.fail`) |
| Verification scripts | `scripts/repro/verify-002-006.ts`, `scripts/repro/verify-keyboard.ts` (results in `evidence/verification/`) |

## When it happens
Only when the page **jumps** to the "Laporkan tulisan" link and it is activated right away:
keyboard navigation (focus moves the page to the link, then Enter) or anything else that scrolls
the link into view instantly. Reading down with the mouse wheel or the End key and then clicking
does **not** trigger it. This narrows the first report, which described it as intermittent for
every reader.

## Steps to reproduce
1. Open any story on kumparan.com (desktop).
2. Using the keyboard, move focus to **Laporkan tulisan** (Tab) and press **Enter**.
3. Look at the address bar while the "Laporkan Konten" form is on screen.

## Expected result
The address bar stays on `/report/story/<slug>` while the report form is displayed.

## Actual result
The form is displayed, but the URL is rewritten back to the story URL. In one recorded desktop
attempt it was rewritten **9 times within 4 seconds** after reaching `/report/story/<slug>`:

```
/kumparannews/<slug>
/report/story/<slug>
/kumparannews/<slug>   (x9, while the report form stays on screen)
```

This points to the article's scroll/URL tracker (the listener that switches to `/full`) still
running after the reader has navigated to the report route: a listener that is not cleaned up
when the article unmounts.

## Scope and suggested fix
Desktop via the keyboard path (deterministic). On mobile only an instant programmatic jump
reproduced it (1/3); no user-like mobile path did. Fix: remove the article's scroll/history
listeners on unmount (or guard them with the current route) so they cannot rewrite the URL of
another page.
